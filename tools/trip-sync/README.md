# Trip-sync: перенос manual-данных с флешки на прод

Инструментарий для сценария «ввод справочников Manual в поездке на загрузочной
флешке, перенос результата на прод через SQL» (август 2026).

## Идея

У каждой таблицы один хозяин. По коду проекта таблицы разделены на три группы:

| Группа | Таблицы | Кто пишет | Как переносим |
|---|---|---|---|
| **Свои** | `tables-owned.txt`: manuals, units, все `manual_*`-конструктор, master_rules*, processes, planes/builders/scopes | только вы (админ-конструктор) | замена таблиц целиком |
| **Совместные** | `tables-shared.txt`: components, process_names + media | вы И прод (components — мобильный Log Card, process_names — EC в TDR-флоу, media — фото на проде) | локальная копия работает в своей «полосе» id (шаг 10 000 000, новая полоса на каждый цикл — см. trip-offset.txt), перенос REPLACE/INSERT-дельтой |
| **Продовые** | всё остальное (workorders, tdrs, wo_*, локи `manual_part_locks`/`manual_process_name_locks`, `manual_user_permissions`, trainings, rm_reports, marketing_*, tasks…) | прод | не трогаем вообще |

Сознательно НЕ включены в перенос (добавьте в `tables-owned.txt`, если будете
их вести в поездке и на проде их никто не правит): `paints`, `conditions`,
`codes`, `necessaries`, `materials`, `machining_work_steps`.

## Два режима работы

Основной режим — **прямо на проде** (aviatechnik.ca, обычный браузер): данные
сразу на месте, скрипты не нужны. **Локальный режим** (флешка) — запасной, на
случай отсутствия связи. Правила переключения:

- **прод → локалка**: обязательно `refresh-local.sh <свежий дамп прода>` —
  иначе локальная копия не знает о введённом на проде, и «свои» таблицы
  разойдутся по id (предохранитель потом заблокирует импорт).
- **локалка → прод**: сначала `export-manual.sh` → `import-prod.sh` (донести
  сделанное), и только потом работать на проде.
- Золотое правило: **между двумя синхронизациями данные вводятся только в
  одном месте.**

## Дисциплина (без неё схема не работает)

1. Пока вы работаете локально, на проде никто (включая вас через браузер!)
   не создаёт/не правит manuals, units и прочие «свои» таблицы.
   (Предохранитель в import-prod.sh это проверяет.)
2. В поездке в **совместных** таблицах (components, process_names) можно
   создавать новое и править — но не удалять физически (soft-delete через UI —
   можно, он переносится). Старые вложения media в поездке не удалять.
3. Флешка перед отъездом заливается **свежим дампом прода**, не домашней базой.
4. Если в поездке менялся код (миграции) — на прод сначала код+миграции, потом
   данные.

## Цикл

### Перед отъездом (один раз)
1. Свежий полный дамп прода → развернуть в базу на флешке.
2. Скопировать актуальный `storage/app/public` прода на флешку (нужно для
   превью существующих вложений; как минимум — ничего, если место жалко).
3. `./prepare-trip.sh` — займёт новую полосу id и запишет `baseline.tsv`.

### Переключение прод → локалка (в поездке, перед каждой локальной сессией)
1. Снять с прода дамп (SSH: `mysqldump`; или экспорт нужных таблиц в
   phpMyAdmin — минимум owned+shared+media), скачать на флешку.
2. `./refresh-local.sh prod-dump.sql.gz` — зальёт и сам вызовет prepare-trip.sh.

### В поездке (в конце каждой сессии)
```
./export-manual.sh
```
Получившийся `~/trip-manual-ГГГГ-ММ-ДД.tar.gz` — себе в Telegram (Избранное).
Это одновременно и резервная копия, и посылка для прода.

### Перенос на прод
Со свежим архивом:
```
DB_USER=... DB_PASS=... DB_NAME=... ./import-prod.sh trip-manual-....tar.gz
tar xzf files.tar.gz -C /путь/к/avia/storage/app/public
```
Скрипт сам: проверит предохранитель → снимет страховочный дамп → применит.

### Через phpMyAdmin (если на хостинге нет SSH)
1. Распаковать архив локально.
2. Предохранитель руками: для нескольких «своих» таблиц выполнить
   `SELECT MAX(id) FROM manuals; SELECT MAX(id) FROM units;` и сверить с
   `baseline.tsv` — на проде не должно быть больше.
3. Экспортировать в phpMyAdmin затрагиваемые таблицы (страховка).
4. Импортировать по порядку: `owned.sql` → `shared-replace.sql` → `media-new.sql`.
5. Файлы: залить содержимое `files.tar.gz` в `storage/app/public/` через
   файловый менеджер хостинга (папки с числовыми именами ≥ 10000000).

### После возвращения
Домашняя OSPanel-копия обновляется свежим полным дампом прода (прод — главный).
Перед заливкой привычный страховочный дамп домашней базы.

## Ограничения — знать и не удивляться

- Физическое удаление строк в совместных таблицах не переносится (только
  soft-delete). В «своих» таблицах переносится всё, включая удаления.
- Конфликт правок одной и той же строки (вы и прод правили один component) —
  побеждает версия с флешки, молча. Правьте в поездке только то, что ваше.
- `media-new.sql` использует INSERT IGNORE: повторный импорт того же архива
  безопасен; для components/process_names повторный REPLACE тоже безопасен.
- Скрипты берут доступ к БД из переменных окружения `DB_NAME`/`DB_USER`/
  `DB_PASS` (по умолчанию root без пароля, база avia).

## Репетиция дома (чек-лист, до отъезда!)

1. На флешке: залить дамп домашней базы → `prepare-trip.sh` → создать тестовый
   manual + пару units/components + загрузить PDF → `export-manual.sh`.
2. Дома в OSPanel: применить архив `import-prod.sh` (это и есть репетиция
   прода) → открыть сайт → новый manual на месте, PDF открывается, старые
   workorders живы.
3. Проверить путь медиа: у новых media id ≥ 10000000 и папки
   `storage/app/public/1000000x/` существуют.
