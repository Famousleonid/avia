# Quantum bridge: доступ, WO history и Codex

Проверено 04/Nov/2026. Это инструкция для будущих сессий, а не постоянное разрешение на удалённые изменения. Перед действиями прочитать `connection-and-safety.md` и проектные правила. Quantum Oracle — только SELECT.

## Доступ

- Мостик: Windows `AVIA-BRIDGE`, `192.168.0.212`, каталог `C:\avia`.
- SSH: стандартный пользователь `codexdiag`; проверенный `whoami`: `avia-bridge\codexdiag`.
- Локальный приватный ключ: `storage/app/codex/codex_bridge_192_168_0_212.key`; known hosts: `storage/app/codex/bridge_known_hosts`. Оба остаются локальными ignored-файлами. Не выводить содержимое ключа, не коммитить и не переносить секреты через чат.
- Рабочая команда из корня репозитория:

```powershell
& 'C:\WINDOWS\System32\OpenSSH\ssh.exe' -i storage\app\codex\codex_bridge_192_168_0_212.key -o BatchMode=yes -o ConnectTimeout=8 -o StrictHostKeyChecking=yes -o UserKnownHostsFile=storage/app/codex/bridge_known_hosts codexdiag@192.168.0.212 'whoami'
```

- Не использовать `StrictHostKeyChecking=no` или `UserKnownHostsFile=NUL`. При изменении host key остановиться и проверить причину. На новом рабочем месте доступ и доверие к хосту настраиваются отдельно.
- Сначала проверить TCP 22. Сетевой запрет sandbox не равен недоступности мостика: повторять конкретную разрешённую проверку через штатное повышение доступа инструмента.
- Причина тайм-аута 04/Nov/2026: sshd слушал порт 22, активен Public-профиль, правило `Codex diagnostics SSH` разрешало старый клиент `192.168.0.127`. Пользователь изменил RemoteAddress на `192.168.0.138`, после чего SSH заработал. IP клиента может измениться; проверять текущий адрес. Не отключать firewall и не открывать SSH всем.
- `codexdiag` не администратор. Через SSH `Get/Export-ScheduledTask` возвращал CIM Access denied. Это не означает отсутствие задачи. Копирование в `C:\avia\WO` и чтение лога доступны; создание SYSTEM-задачи требует административного контекста и разрешения пользователя.

## Защищённые существующие синхронизации

При работе с WO не изменять и не перезапускать `sync_quantum`, `C:\avia\RO`, photo/archive sync, их конфигурации и credentials. Чтение существующего `C:\avia\RO\.env.sync_quantum` отдельным WO runner разрешено в рамках запуска; файл не редактируется. Не выводить его содержимое. Разрешение на WO не распространяется на RO или media.

## Unit History: установленное состояние

- Источник кода: `C:\OSPanel\domains\avia.loc\WO`; мостик: `C:\avia\WO`.
- 04/Nov/2026 скопировано 16 файлов, SHA256 каждого совпал. При повторном копировании сначала проверить destination и различия; не удалять логи/настройки и не перезаписывать чужие изменения молча.
- Отдельная задача: `\sync_quantum_unit_history`, SYSTEM, ежедневно 06:30 по часовому поясу мостика (`Eastern Standard Time`, с правилами перехода Windows).
- Установщик: `C:\avia\WO\install_unit_history_task.ps1`. Создаёт/обновляет только эту задачу и запускает первую выгрузку; запускать после разрешения пользователя, предварительно проверив, не выполняется ли она уже.
- Runner: `C:\avia\WO\run_unit_history.ps1`; exporter: `unit_history_export.php`; лог: `C:\avia\WO\unit_history_sync.log`.
- Получатель: `https://aviatechnik.ca/api/quantum/unit-history`. Пользователь явно подтвердил 04/Nov/2026 передачу истории WO сейчас и ежедневно в 06:30: WO, P/N, S/N, customer, даты, статус, количества. Токен используется только внутри bridge-процесса.
- Первая выгрузка 04/Nov/2026 09:54:34–09:54:37: `8184 Quantum WO rows exported`, `SUCCESS`; установщик подтвердил следующий запуск 05/Nov/2026 06:30.
- JSON snapshot хранится на сайте в `storage/app/quantum/unit-history.json`. Лог мостика — диагностика, не источник таблицы. Экспортёр с `--send` отправляет JSON в API; локальный JSON на мостике по умолчанию не сохраняет.

Установка/повторная установка в административном PowerShell (после разрешения; включает upload):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\avia\WO\install_unit_history_task.ps1
```

При уже установленной задаче для ручного обновления предпочитать запуск существующей `sync_quantum_unit_history` из административного контекста, а не переустановку. Не запускать параллельно с текущей выгрузкой. Проверять LastTaskResult, NextRunTime и свежий SUCCESS в логе. Одно наличие задачи не доказывает доставку. После изменений кода сверять SHA256. Не выдавать ожидаемые данные за проверенные.

## Связь с Codex на мостике

- На мостике есть отдельное приложение Codex и существующий чат, начинающийся `Ты работаешь на Quantum bridge computer.`. Находить его по свежему экрану/списку, не сохранять window ID или координаты как постоянные.
- Сопряжение через Settings → Подключения → Управление этим ПК выполнено; видны «Разрешить подключения» и управляющее устройство `Windows NT 10.0 x64`. Однако инструменты текущего чата показывали только host `local`: сопряжение НЕ доказывает доступ к удалённым чатам/файлам и НЕ объединяет память агентов.
- Сначала проверить доступные hosts/projects/threads. Если удалённый чат доступен через специальный инструмент, использовать его. Отправлять задания другому Codex только по явному поручению пользователя; передавать цель, ограничения и ожидаемый отчёт, без секретов.
- В этой сессии пользователь явно поручил написать в Codex мостика; сообщение было отправлено через его открытый чат в RDP. Агент диагностировал неверный IP firewall, но его повышение прав отклонила политика. Не считать текст «сделаю» или индикатор работы выполненным исправлением; читать финальный результат и проверять SSH самостоятельно.
- RDP clipboard оказался несинхронизирован: `typeText` вставил старую картинку вместо текста. Удалили случайное вложение до отправки; ввод отдельными `pressKey` в английской раскладке сработал. При повторении проверять черновик перед отправкой. Не отправлять старое содержимое буфера.
- Для UI всегда соблюдать актуальные ограничения инструментов и навыков. Предыдущий успешный ввод не является разрешением обходить новые ограничения, UAC, запросы подтверждения или отказ auto-review. Если действие требует подтверждения, назвать конкретное действие/получателя и причину; после подтверждения продолжать, не спрашивая то же снова.
- При отказе автоматической проверки не обходить его другим каналом. В этом случае запуск upload был разрешён после явного подтверждения пользователем HTTPS-получателя и состава данных. Будущие изменения назначения/состава/доступов оценивать заново.

## Порядок следующей работы

1. Прочитать эту инструкцию, установить разрешённый пользователем объём работ.
2. Проверить SSH существующим ключом; при проблеме различить network, authentication и administrative permissions.
3. Прочитать текущие WO-скрипты, лог и состояние отдельной задачи, не затрагивая RO/media.
4. Выполнить только разрешённый перенос/запуск/настройку. Если инструмент требует отдельного подтверждения, соблюдать его.
5. Подтвердить результат логом, статусом задачи и при необходимости чтением сайта. Сообщить количество, время, расписание и ограничения.
