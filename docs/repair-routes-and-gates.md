# Repair Routes & Gates — дизайн развития движка Measurements

Статус: **DRAFT — согласован концептуально** (сессия 26.08.2026)
Референс-кейс: род с ball bearing (5 сценариев, см. §4)

---

## 1. Итоговая модель (словарь)

**Место (parameter / inspection point)** — точка на детали: отверстие под bearing,
основная хромированная поверхность, резьба. У места есть размеры (orig/wear),
возможные дефекты (коды с контекстом) и набор **маршрутов**.

**Маршрут (repair rule)** — полный альтернативный сценарий ремонта ОДНОГО места:
триггеры («что нашли») + упорядоченный список процессов («что делать»).
У места может быть несколько маршрутов; активен всегда **не более одного**.

**Гейт** — процесс маршрута с флагом `is_gate`: точка, где появляется вердикт
(замер или инспекция) и хвост плана может смениться. Существующий EC-гейт по
финальным замерам — частный случай.

**Переключение маршрута на гейте** — новый примитив: finding, полученный на
гейте, может активировать другой маршрут **того же места**, замещающий текущий.
Начатые процессы остаются историей, незапущенный хвост пересобирается.

**План детали** = «лучший известный план при текущем наборе findings».
Findings приходят порциями (входная инспекция → после strip → NDT → финальные
замеры); после каждой порции пересобирается только незапущенный хвост.
Явное дерево сценариев НЕ моделируется — оно существует неявно:
набор маршрутов мест × гейты.

**Default routes НЕ вводим.** Все маршруты триггерные (решение сессии:
и замена bearing, и рехром — условные). Lifecycle «TDR от FAIL/finding»
сохраняется. «Штатная» работа (silver в отверстии) — часть маршрута замены
bearing, а не самостоятельный default.

## 2. Scope-политика процессов

- **part-scope**: ванны (chrome, silver, cad), печи (bake/stress relief), NDT —
  одна строка на деталь, аккумулирует process_ids всех маршрутов.
  Общие part-scope узлы служат «якорями» глобального порядка:
  все резки → NDT → ванна → все шлифовки — получается топосортировкой без спец-кода.
- **point-scope**: резание (расточка, шлифовка конкретной поверхности), локальные
  операции — отдельная строка на каждое место.

Ловушка слияния part-scope: узлы сливаются по (имя, номер вхождения в правиле).
Если маршруты содержат процесс разное число раз — проверять результат в превью.

## 3. Гейты: два вида вердикта

| Вид | Пример | Как записывается |
|-----|--------|------------------|
| Замер | база после strip chrome (мин. диаметр = макс. толщина хрома) | обычный замер отдельного параметра «Base metal dia (after strip)» со своими лимитами |
| Инспекция | отверстие после снятия bearing; NDT после machining/strip | finding-запись в `wo_measurements` по месту, код из общего словаря (Damage, Corrosion, Crack…), новый контекст |

Оба вердикта пишутся через `wo_measurements` — тогда они двигают
`last_synced_measurement_id` и переармируют кнопку/превью пересборки.

**NDT**: новый тип триггера `finding_ndt`. Вердикт вводится по местам
(трещина в отверстии ≠ трещина на штоке — сценарии разные). PASS — отметка
«гейт пройден», хвост не меняется. Crack(место) → матчится маршрут этого места
(weld / scrap `action=order_new` / EC). Гейт может срабатывать многократно
(weld → повторный NDT).

Промежуточный контроль базы — **отдельным параметром** (вариант 1),
третью стадию замера (initial/base/final) не вводим, пока таких контролей мало.

## 4. Референс-кейс: род с ball bearing

Места и маршруты:

```
Место «Bearing bore»:
  R1 «Replace bearing»                триггер: finding[Bearing worn/play]
     Снять bearing → [ГЕЙТ: инспекция отверстия] → Silver → Установить новый bearing
  R2 «Replace bearing + chrome in hole»  триггер: finding на гейте [Damage/Corrosion]
     Снять bearing → Расточка → NDT → Chrome → Шлифовка → Установить новый bearing
     (замещает R1 на гейте; «Снять bearing» уже начат → история)

Место «Основная поверхность»:
  R3 «Rechrome»                       триггер: finding[Chrome worn/damaged] или FAIL
     Strip chrome → [ГЕЙТ: замер базы] → Шлифовка базы → NDT → Chrome → Шлифовка в размер
```

Сценарии (все подтверждены пользователем):

| # | Findings | Правила | Особенности плана |
|---|----------|---------|-------------------|
| 1 | bearing worn; chrome worn | R1+R3 | NDT одной строкой; ванны silver и chrome раздельные |
| 2 | bearing worn; chrome ok | R1 | только silver-цепочка |
| 3 | bearing worn; hole damage (гейт); chrome worn | R2+R3 | Chrome ОДНОЙ ванной на оба места; NDT общий; шлифовки по местам |
| 4 | bearing worn; hole damage (гейт); chrome ok | R2 | chrome только в отверстии |
| 5 | chrome worn (bearing ok) | R3 | отверстие/bearing не трогаются |
| 6 | ничего | — | serviceable, плана нет |

## 5. Заказ деталей из маршрута (linked part orders) — НОВОЕ

Сегодня: bearing заказывается отдельным **ручным** Order New TDR рядом с
ремонтным TDR рода. Требование: этим надо управлять из маршрута.

Дизайн:

- **Декларация на правиле**: маршрут может требовать заказ компонентов —
  таблица `manual_parameter_rule_part_orders`
  (`repair_rule_id`, `component_id` | `ipl_num`, `qty`, `note`).
  У рода: R1 и R2 оба заказывают bearing (заказ нужен при любом маршруте замены).
  Это закрывает дыру модели «action = repair ИЛИ order_new»: ремонтный маршрут
  может попутно заказывать детали, не меняя свой action.
- **Активация**: при применении маршрута (создание TDR / пересборка) система
  поднимает **связанный Order New TDR** на компонент:
  `tdrs.source_rule_id` + `source_tdr_id` (ссылка на ремонтный TDR детали-носителя).
  Дедуп: один активный авто-заказ на (workorder, component, место-источник).
- **Управление (ключевое требование)**:
  - заказ виден и подтверждается в **превью пересборки** («будет заказан:
    bearing P/N …, qty 1 — из маршрута R1»); техник может снять галку;
  - qty редактируется (по умолчанию из декларации × кол-во мест);
  - при **смене маршрута на гейте**: если новый маршрут тоже декларирует этот
    компонент — заказ сохраняется (перепривязывается source_rule_id);
    если нет — превью предлагает отменить связанный заказ
    (не отменяет молча: заказ мог уже уйти поставщику);
  - при revert ремонтного TDR — связанные авто-заказы удаляются вместе с ним
    (если по ним не началась работа/закупка);
  - ручные Order New TDR продолжают работать как раньше; связанные помечаются
    в UI бейджем «auto · from route» со ссылкой на место/правило.
- **Статусы закупки** (ordered/received…) — вне scope этого дизайна,
  используется существующий lifecycle TDR.

## 6. Превью пересборки (Update) — всегда с подтверждением

**СДЕЛАНО 26.08** (кроме секции заказов — придёт с §5):

- endpoint `POST /workorders/{wo}/update-part-processes/preview`
  (`previewPartProcesses`) — dry-run: ничего не пишет, sync point не двигает;
- дифф по узлам плана (`rowCoversGroup`): **Added / Removed / Kept (started
  history) / Unchanged**;
- **выбор маршрута точки**: когда точке подходит >1 правила — радио в модалке;
  `rule_overrides` (param_id → rule_id) в превью применяются in-memory,
  при Apply — персистятся во ВСЕ FAIL-замеры точки (закрывает B для пересборки);
- **фикс D**: правила с action=order_new/ec исключены из mainRuleIds и
  показываются предупреждениями (превью + ответ Apply + toast) — больше не
  растворяются в ремонтном плане;
- UI: модалка `msUpdPrevModal` в `_tab.blade.php`, поток в tab.js — кнопка
  Update всегда открывает превью; смена радио перезапрашивает превью.

Осталось на будущее: секция «заказы» (§5), авто-открытие превью по вердикту
гейта (§3/этап 4). Рефакторинг: общий `rebuildContext()` +
`plannedGroups()` + `matchingRules()` (бэкенд-зеркало tdrMatchingRules).

## 8. Порядок реализации

1. Фиксы A + B + C (+ тесты на пересборку) — фундамент.
2. Превью пересборки (дифф-модалка) — сразу закрывает D, даёт место конфликтам.
3. Linked part orders (§5): декларация на правиле + авто-TDR + управление в превью.
4. Гейт-вердикты через wo_measurements: инспекция отверстия (переключение
   маршрута места), затем NDT (`finding_ndt`) с вводом по местам.
5. Параметр «база после strip» + его гейт (реюз EC-гейт механики).
