# Repair Routes & Gates — дизайн развития движка Measurements

Статус: **DRAFT — согласован концептуально** (сессия 26.08.2026)
Референс-кейс: род с ball bearing (5 сценариев, см. §4)

---

## 1. Итоговая модель (словарь)

**Место (parameter / inspection point)** — точка на детали: отверстие под bearing,
основная хромированная поверхность, резьба. У места есть размеры (orig/wear),
возможные дефекты (коды с контекстом) и набор **маршрутов**.

**Маршрут (repair rule)** — полный альтернативный сценарий ремонта ОДНОГО места:
триггеры («что нашли») + упорядоченный список процессов («что делать»).
У места может быть несколько маршрутов; активен всегда **не более одного**.

**Гейт** — процесс маршрута с флагом `is_gate`: точка, где появляется вердикт
(замер или инспекция) и хвост плана может смениться. Существующий EC-гейт по
финальным замерам — частный случай.

**Переключение маршрута на гейте** — новый примитив: finding, полученный на
гейте, может активировать другой маршрут **того же места**, замещающий текущий.
Начатые процессы остаются историей, незапущенный хвост пересобирается.

**План детали** = «лучший известный план при текущем наборе findings».
Findings приходят порциями (входная инспекция → после strip → NDT → финальные
замеры); после каждой порции пересобирается только незапущенный хвост.
Явное дерево сценариев НЕ моделируется — оно существует неявно:
набор маршрутов мест × гейты.

**Default routes НЕ вводим.** Все маршруты триггерные (решение сессии:
и замена bearing, и рехром — условные). Lifecycle «TDR от FAIL/finding»
сохраняется. «Штатная» работа (silver в отверстии) — часть маршрута замены
bearing, а не самостоятельный default.

## 2. Scope-политика процессов

Критерий (уточнён 26.08 на роде 32-31-02): **part-scope** — операция физически
одна на деталь И одинакова для всех мест (печи bake/stress relief, NDT, paint);
**point-scope** — у каждого места свои параметры или своя постобработка.

- part-scope: одна строка на деталь, аккумулирует process_ids всех маршрутов.
  Общие part-scope узлы служат «якорями» глобального порядка:
  все подготовки → NDT → … → финиш — получается топосортировкой без спец-кода.
- point-scope: отдельная строка на каждое место. Резание (расточка, шлифовка) —
  всегда point. **Покрытия — тоже point**, когда места кроются по-разному:
  у рода хром основной поверхности кладётся с припуском и шлифуется в размер,
  а хром key/отверстия напыляется на заданную толщину без постобработки —
  это разные строки плана с разными продолжениями маршрута. Требуемая толщина /
  «grind to size» пишутся в description процесса правила — попадают в план и печать.

**Соседние NDT сворачиваются (27.08)**: идущие подряд NDT-x строки плана
объединяются в одну комбинированную (NDT-1 / NDT-4) через существующий
`TdrProcess.plus_process` (мульти-NDT строка, печать одной формой);
операции/rule_process_ids обеих строк сохраняются. Несоседние NDT остаются
раздельными — между ними есть работа. Превью показывает комбинированное имя.

**Приоритет плана (`process_names.plan_order`, 27.08)**: цепочки маршрутов —
жёсткие ограничения, но среди ОДИНАКОВО ГОТОВЫХ узлов топосортировка
предпочитает меньший plan_order (null = 100). Логистика площадки: machining /
stress relief / paint — in-house, большинство остального — вендоры; Machining
(и Machining (EC)) = 10 → вся механика выполняется в начале плана, деталь
уезжает к вендору один раз. Пример (chrome in hole + keys): Machining расточка →
Machining blend-out → strip → NDT-1 → покрытия → Passivation → NDT-4 → Paint.

**Слияние part-scope — по ОПЕРАЦИИ (27.08)**: узлы сливаются по (имя, операция,
номер вхождения). Одно имя + одна операция → одна строка на деталь (в неё
стекаются rule_process_ids всех маршрутов); одно имя + РАЗНЫЕ операции →
отдельные строки по порядку (Bake AMS 2759/9 и /11, Chrome Type I и Type II).
Chrome stripping переведён в part-scope (одна ванна на деталь).

## 3. Гейты: два вида вердикта

| Вид | Пример | Как записывается |
|-----|--------|------------------|
| Замер | база после strip chrome (мин. диаметр = макс. толщина хрома) | обычный замер отдельного параметра «Base metal dia (after strip)» со своими лимитами |
| Инспекция | отверстие после снятия bearing; NDT после machining/strip | finding-запись в `wo_measurements` по месту, код из общего словаря (Damage, Corrosion, Crack…), новый контекст |

Оба вердикта пишутся через `wo_measurements` — тогда они двигают
`last_synced_measurement_id` и переармируют кнопку/превью пересборки.

**NDT — СДЕЛАНО 27.08 (этап 4 core)**: триггер `finding_ndt` (enum расширен),
контекст кода `ndt` на параметре (Add defect code → NDT); вердикт вводится как
обычный finding-замер по месту → авто-резолв по finding_ndt (точный код →
wildcard). **Замещение маршрута**: активное правило места = правило ПОСЛЕДНЕГО
FAIL-вердикта точки (union больше не делается) — NDT-crack, введённый после
размерного FAIL, замещает silver-маршрут weld-маршрутом; начатые строки —
история (скип по узлу), незапущенный хвост пересобирается через превью.
Связанный заказ при смене маршрута перепривязывается к новому правилу
(source_rule_id), если тот тоже декларирует компонент.
**Scrap-вердикт (27.08, проверено на wo107903)**: активное правило
action=order_new = деталь-НОСИТЕЛЬ списана → превью: красный блок «Scrap —
order replacement». Заказывается **assy носителя** (через ComponentAssembly:
род 1-375B → Rod Assy 1-370B), голая деталь — только если assy не заведена.
NDT-контекстный вердикт даёт код заказа **Failed NDT** (иначе — код вердикта).
Связанные заказы носителя (bearing) при scrap помечаются к отмене с галкой
ПО УМОЛЧАНИЮ — входят в заказываемую сборку. **План при scrap НЕ
пересобирается**: в блоке селектор «Work completed through» (по умолчанию —
ПЕРВАЯ NDT-строка) — строки до точки остаются записью выполненного (цех
работает и без дат на процессах; строки с date_start сохраняются всегда),
хвост удаляется. Дедуп замены — по позиции. Вердикт, не сматчивший ни одного
правила, даёт предупреждение (прежний маршрут сохраняется, молча не глотается).
Ввод вердикта в Inspect — кнопка «Add NDT / in-process finding» (у точек с
NDT-кодами). Удаление вердикт-замера сбрасывает sync point → Update
переармируется и возвращает прежний план (полный цикл туда-обратно проверен).
Отложено: авто-подсказка при закрытии гейт-процесса (`is_gate`) в traveler-флоу.

Промежуточный контроль базы — **отдельным параметром** (вариант 1),
третью стадию замера (initial/base/final) не вводим, пока таких контролей мало.

## 5. Заказ деталей из маршрута (linked part orders) — СДЕЛАНО 27.08

- **Декларация на правиле**: `manual_parameter_rule_part_orders`
  (`repair_rule_id`, `component_id`, `qty`, `note`); блок «Order parts» в
  редакторе правила (селект из Parts мануала + qty). У рода: правила 16 и 17
  (оба маршрута точки 6) заказывают bearing 1-380A. Закрывает дыру
  «action = repair ИЛИ order_new»: ремонтный маршрут попутно заказывает детали.
- **Превью Update — секция «Parts to order»**:
  - `proposed` — маршрут декларирует, заказа нет → чекбокс (по умолчанию
    включён) + qty; Apply поднимает **связанный Order New TDR**
    (`tdrs.source_rule_id` + `source_tdr_id` на ремонтный TDR носителя);
  - `existing` — заказ на компонент уже есть (авто или ручной, как TDR 1557
    у рода) → строка «Already ordered», дубль не создаётся;
  - `obsolete` — связанный заказ, чей компонент больше не декларируется
    активными маршрутами → чекбокс «Cancel order» (по умолчанию ВЫКЛЮЧЕН,
    молча не отменяется). Отмена работает и когда правил не осталось совсем.
- **Точка невозврата**: `po_num` или `received` на заказе → отмена
  отказывается (warning в ответе и toast), revert тоже не трогает такой TDR.
- **Revert ремонтного TDR** удаляет его связанные авто-заказы (без PO/receipt).
- Ручные Order New работают как раньше и участвуют в дедупе.
- Тесты: `test_linked_part_order_lifecycle` (proposed → создан со связями →
  existing без дубля → obsolete → отменён), `test_linked_order_with_po_is_not_cancelled`.
- **Позиции и варианты (27.08)**: дедуп заказов — по позиции IPL (базовый
  номер без буквенного суффикса), НЕ по P/N: один P/N живёт на разных позициях
  (1-380 род / 1-400 цилиндр) и обе заказываются. Вариант позиции для WO
  выбирается через **assy-группировку Parts** (ComponentAssembly): из вариантов
  позиции берётся тот, чьи assy пересекаются с assy детали-носителя
  (какой род → какой bearing); фолбэки: assy юнита WO → задекларированный
  компонент как есть (позиции с незаполненными assy ведут себя по-старому).
  Заказ наследует codes/conditions носителя (NULL codes выпадал из
  Ordered Parts/PRL из-за SQL-сравнения с NULL).
- Осталось из дизайна: перепривязка source_rule_id при смене маршрута
  (сейчас заказ просто остаётся existing — компонент декларируют оба маршрута
  рода, чего достаточно); бейдж «auto · from route» в списке TDR.

## 6. Превью пересборки (Update) — всегда с подтверждением

  (`previewPartProcesses`) — dry-run: ничего не пишет, sync point не двигает;

## 8. Порядок реализации

1. Фиксы A + B + C (+ тесты на пересборку) — фундамент.
2. Превью пересборки (дифф-модалка) — сразу закрывает D, даёт место конфликтам.
3. Linked part orders (§5): декларация на правиле + авто-TDR + управление в превью.
4. Гейт-вердикты через wo_measurements: инспекция отверстия (переключение
   маршрута места), затем NDT (`finding_ndt`) с вводом по местам.
5. Параметр «база после strip» + его гейт (реюз EC-гейт механики).

## 8a. Триггеры с порогом («этап 2.5») — СДЕЛАНО 26.08

Реальный кейс (род 32-31-02, точка 6, отверстие bearing): silver восстанавливает
выработку только до толщины слоя (~0.006–0.010" по диаметру); выше — расточка +
chrome. Оба маршрута триггерятся `above_orig`, различаясь ВЕЛИЧИНОЙ превышения.

Реализация: `manual_parameter_rule_triggers.min_delta / max_delta` (nullable,
только размерные триггеры). Превышение = насколько замер вышел за лимит со
стороны триггера; полосный триггер срабатывает при `min_delta < Δ ≤ max_delta`
(null-границы открыты; граница включена в нижнюю полосу). Оба null → прежнее
поведение. Полосный триггер требует превышения именно на СВОЕЙ стороне лимита
(`acceptsExceedance`). Учитывается в: `resolveRepairRule` (store + пересборка),
`matchingRules` (опции превью — при полосах остаётся одна, радио не нужно),
`tdrMatchingRules` (tab.js), редактор правил (инпуты «over > Δ» / «up to ≤ Δ»,
бейдж Δ в списке правил).

Пример: Silver `above_orig max_delta=0.010`; Chrome in hole `above_orig
min_delta=0.010`. Замер 10.105 при max 10.1 → Δ=0.005 → Silver; 10.150 →
Chrome; ровно 0.010 → Silver.

**Правило orig/wear (подтверждено 27.08)**: wear-лимиты есть не всегда — при их
отсутствии применяются orig-лимиты НЕЗАВИСИМО от режима WO, и семейство
триггеров следует за фактически применёнными лимитами
(`effectiveLimits()['source']`), а не за флагом WO (фикс 03a1799: wear-режимный
WO «Repair» + параметр без wear-лимитов → orig-триггеры матчатся). Если у
параметра wear-лимиты ЕСТЬ, на не-overhaul WO работают они — и правила точки
должны иметь wear-триггеры со своими порогами (база превышения другая);
авто-подмена wear→orig триггеров сознательно НЕ делается.

## 8b. Условные процессы в правиле — СДЕЛАНО 27.08

Кейс (род, NDT-4): при «только замена bearing» контроль (NDT-1 + NDT-4) идёт ДО
серебра; но если в том же плане есть хром-маршрут — общий NDT-4 идёт ПОСЛЕ
серебра (проверяет и серебро).

Реализация: `manual_parameter_rule_processes.condition` (JSON, nullable):
`{"type":"has_process"|"not_has_process","process_name_ids":[..]}` — строка
применяется в зависимости от содержимого СЛИТОГО плана. План для оценки условий
= process_name ids БЕЗУСЛОВНЫХ строк всех сматченных правил (один проход, без
fixpoint). Неприменившаяся строка выпадает БЕЗ разрыва цепочки (соседи
связываются напрямую). Оценка в TopologicalProcessMerger → работает везде
(создание TDR, пересборка, превью, EC).

Маршрут Silver рода: NDT-1 → NDT-4[not_has Chrome plating] → Silver →
NDT-4[has Chrome plating] → Paint. Silver-only: NDT-1 → NDT-4 → Silver → Paint;
комбинированный: strip → NDT-1 → shot → Chrome → Silver → NDT-4 → Paint
(часть-scope NDT-4 сливается с NDT-4 хром-маршрута).

UI: кнопка «if» на строке процесса в редакторе правила (цикл: всегда → есть →
нет) + селектор процесса. Известное упрощение: `previewNameIds` (условия
Start/Finish у MasterRule) видит все строки правил без учёта их условий —
надмножество; при необходимости сузить позже.
