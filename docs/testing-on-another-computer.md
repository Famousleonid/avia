# Тесты и работа на другом компьютере

## Что находится в Git

- Код приложения, миграции, `composer.lock`, `package-lock.json`.
- Все тесты из `tests/`, включая новые Feature-тесты.
- Навык `.agents/skills/avia-import-manual-package/` и постоянный журнал его проверок.
- HTML-журнал `output/manuals-production-journal.html` и прежний совместимый путь.
- SQL-аудит тесты `storage/app/codex/manual-package-import/**/test*.php` и аналогичные Python/JS файлы.

`.env`, `.env.testing`, пароли, SSH-ключи, дампы и снимки production, зависимости, логи, изображения сканов и временные файлы не публикуются. Исходные PDF/XLS из `C:\Airplane` находятся вне репозитория: перенесите их отдельно через разрешённое хранилище.

## Запуск PHPUnit

1. Получить актуальный коммит, установить PHP с расширениями проекта, Composer и отдельный локальный MySQL.
2. Выполнить `composer install` (с dev-зависимостями).
3. Создать локальный `.env` по `.env.example`, а `.env.testing` по `.env.testing.example`. Указать локальные реквизиты самостоятельно; не копировать production-секреты.
4. Создать отдельную пустую БД `aviatechnik_testing`. Основная БД из `.env` должна иметь другое имя. **Тесты выполняют `migrate:fresh` и удаляют таблицы в тестовой БД. Не указывать удалённый/production сервер.**
5. Создать тестовый ключ приложения: `php artisan key:generate --env=testing`. Проверить отсутствие устаревшего локального кэша конфигурации.
6. Запускать последовательно, по одной команде:

```text
php artisan test --testsuite=Unit
php artisan test --filter=InProcessCheckSheetTest
php artisan test --filter=PartGroupsTest
php artisan test
```

Несколько процессов `php artisan test` одновременно запускать нельзя: используется общая тестовая БД. Bootstrap определяет каталог скомпилированных представлений относительно текущего checkout, без привязки к `C:\OSPanel`.

## Тесты конкретных SQL-пакетов

Это отдельные аудиты конкретных импортов, не часть стандартного PHPUnit. Код тестов сохранён в исходных каталогах, чтобы относительные пути оставались прежними. Для их запуска нужны соответствующие проверенные `*_import.sql`, `*_verify.sql`, source JSON, графы и локальные входные снимки из папки конкретного запуска. Они не становятся доступными от одного `git clone`.

Переносить полный run-каталог следует отдельно после проверки содержимого на секреты, с сохранением относительного пути. Без этих входных файлов тест не воспроизводим. Не заменять отсутствующие данные догадками и не запускать такой тест против production. Привязанные к этому компьютеру внешние пути в разовых SQL-аудитах нужно сверить перед запуском.

## Журнал

Открыть `output/manuals-production-journal.html` в браузере. Это автономный снимок и журнал подтверждённых проверок, а не онлайн-подключение к production. После новых загрузок данных нужно заново выполнить read-only аудит и обновить журнал. Доступ к production настраивается отдельно; ключи через Git не передаются.
