# Отказ от Legacy Group

## Единые правила

- Буквы в конце IPL (`1-230`, `1-230A`, `1-230B`) обозначают варианты одной позиции внутри одного manual. Для них ручная группа не нужна.
- Разные числовые позиции одной детали объединяются через Alternative P/N.
- Original/Oversize — отдельная группа с возможностью заказа нескольких размеров одновременно.
- ASSY/KIT задают состав, а не объединение всех участников в одну альтернативную позицию.
- Одинаковый P/N в разных IPL сам по себе не объединяет позиции.
- В расчётах больше нет чтения `components.kit_prl_choice_group`. После переноса отдельная миграция удаляет само поле и индекс; неперенесённые связи блокируют удаление. Запись через интерфейс запрещена.
- `Edit → Assemblies` / `component_assemblies` — отдельная совместимость со старыми TDR, не Legacy Group; эта задача её не удаляет.

### Вариант через SQL для production — 17/Sep/2026

**Выполнено пользователем; postflight подтверждён 17/Sep/2026.** Несмотря на сообщение phpMyAdmin `#2014 Commands out of sync` на последующем служебном `SET FOREIGN_KEY_CHECKS = ON`, основной блок завершился: Legacy-поле и индекс отсутствуют, запись миграции есть, резервная таблица содержит 77 связей, созданы 16 групп / 50 вариантов / 50 связей состава. Все проверенные поля 77 исходных Parts и существующие группы #8/#92/#93 с вариантами совпали со снимком до запуска. Доказательства: `storage/app/codex/legacy-production-postflight-20260917.json`. Повторный импорт для устранения сообщения phpMyAdmin не нужен. Вероятный механизм клиентской ошибки — необработанные наборы результатов завершающего SELECT внутри составного блока перед следующим служебным запросом; выполнение SQL через PDO в тесте явно вычитывало эти наборы. Конкретный PHP-код phpMyAdmin не проверялся.

По свежей read-only проверке production перенос ещё не был выполнен: 77 Legacy-связей (75 активных Parts и 2 удалённых), 9 manuals. Рабочий код уже использует PartVariantGrouping. Подготовлен файл `output/sql/legacy_retirement_production_20260917_v01.sql` для импорта в выбранную production-базу через phpMyAdmin. Он рассчитан на проверенную MariaDB 10.6 и использует `BEGIN NOT ATOMIC` / `DELIMITER`, без создания хранимой процедуры.

Перед импортом экспортировать полную БД и исключить редактирование Parts/групп и печать на время операции. SQL проверяет точные исходные ID/IPL/P/N/названия/количества/Legacy-значения и существующие группы; любое расхождение останавливает перенос. Сами Parts, их количества, ASSY и WO не изменяются.

Таблица `codex_legacy_group_backup_20260917` сохраняет 77 исходных связей и остаётся в базе как архив (не используется логикой приложения). После транзакционного переноса удаляются поле и индекс Legacy и регистрируется соответствующая Laravel-миграция. DDL не откатывается транзакцией, поэтому полная резервная копия обязательна. Повторный запуск и возобновление после фиксации данных до удаления схемы проверены.

После импорта выполнить `output/sql/legacy_retirement_production_20260917_v01_verify.sql` (только SELECT). Ожидается: поле/индекс 0, архив 77, исходные Parts 77, новых групп 16, всего проверяемых групп 19, запись миграции 1. Не запускать старую production-версию команды `part-groups:retire-legacy` после удаления поля: для последующего CLI-аудита перенести обновлённый `RetireLegacyPartGroups.php`, который поддерживает отсутствие столбца. Сам SQL не требует запуска Artisan.

Тест выполнен на отдельной локальной MariaDB 10.6.9 с production-снимком связей; проверены защита от изменения P/N, создание/переиспользование групп, backup, удаление схемы и два сценария повторного запуска. ### Альтернативный вариант через Artisan

Не переносить числовые ID созданных локально групп через SQL: production уже содержит группы, которых не было в локальной копии. Команда сопоставляет фактический состав и использует существующие группы.

1. Сделать резервную копию production-БД. На время переноса исключить изменения Parts и печать форм.
2. Перенести согласованные версии файлов:
   - `app/Console/Commands/RetireLegacyPartGroups.php`
   - `app/Services/PartVariantGrouping.php`
   - `app/Support/KitPrlGrouping.php`
   - `app/Support/BushingPrlGrouping.php`
   - `app/Services/PartGroupCoverageResolver.php`
   - `app/Services/WorkorderStdProcessItemsService.php`
   - `app/Models/WorkorderStdProcessItem.php`
   - `app/Models/Component.php`
   - `database/migrations/2026_09_17_100000_drop_retired_kit_prl_choice_group.php`
   - `app/Http/Controllers/Admin/ComponentController.php`
   - `app/Http/Controllers/Admin/TdrController.php`
   - `app/Http/Controllers/Admin/TdrPrintFormController.php`
   - `resources/views/admin/manuals/show.blade.php`
   - `resources/views/admin/components/partials/index-rows.blade.php`
3. Выполнить `php artisan part-groups:retire-legacy` — это аудит без изменения БД. При сообщении о конфликте не продолжать, сверить перечисленные группы.
4. Проверить план; выполнить `php artisan part-groups:retire-legacy --apply`. Перед транзакцией команда сохраняет исходные записи в `storage/app/part-groups/`; создание групп и очистка старых значений выполняются вместе. Применение записывается в activity log.
5. Снова выполнить аудит: старых связей должно остаться 0. Проверить KIT, PRL, NDT/CAD/Stress/Paint и их счётчики на рабочих WO.
6. Удалить пустое поле и индекс: `php artisan migrate --path=database/migrations/2026_09_17_100000_drop_retired_kit_prl_choice_group.php --force`. При наличии любых неперенесённых значений миграция остановится до DDL. После удаления команда аудита сообщает `Legacy column already removed. Nothing to migrate.` Откат этой миграции восстанавливает только пустое поле и индекс, а не старые связи. `component_assemblies` и новые Part Groups не удаляются.

Существующие данные `bush_ipl_num` сохраняются как идентификатор семейства для списков бушингов без новой группы. Если новая группа присутствует, для печатной группировки используется именно она. Перенос расширяет семейство до всех деталей с тем же Initial Bushing IPL, а не только до выбранного когда-то подмножества Legacy.

Для отката нужна согласованная предыдущая версия кода и резервная копия БД. JSON фиксирует исходные Parts и план переноса, но не является автоматической полной процедурой отката БД.
