# Общие правила AVIA

Исключение размера печати (29/Oct/2026): по прямому запросу пользователя номера деталей (.part-no-data) в Bushing SP — 10px, независимо от общего минимума12px. При этой правке подписи IPL и KIT не менять.

Traveler heading (29/Oct/2026): логотип закреплён сверху слева внутри повторяемой шапки таблицы; PART TRAVELER 24px и подстрока центрируются по полной ширине листа, не по col-8. Учитывать общие print-правила h1–h6 (16px!important и margin), которые иначе перезаписывают заголовок. Шапку сохранять компактной: WO108085/TDR3456 проверен в Chrome/PDF на одном листе с footer.

Печатные таблицы (29/Oct/2026, уточнение пользователя): минимум 12 CSS px по умолчанию относится только к формам процессов и Traveler. Measurements/F&C сохраняют прежние 9–11px, включая портретную печать; Log Card, SB, TDR, PRL/KIT, Certificate, R&M и Transfers не увеличивать из-за этого требования. SB сохраняет настройки в pt и default8.3pt. Существующие стандартные 13–14px и явно сохранённые Print Settings не сбрасывать. Номера деталей Bushing SP — отдельное исключение10px. Мелкие подписи IPL/KIT не увеличивать дополнительно.

R&M Identification Method (29/Oct/2026): в редакторе WO одно свободное textarea, как Part Description, без select и отдельного Number. При отображении старой строки объединять ident_method + ident_number пробелом и очищать ident_number в клиентской модели; сохранение/печать не дублирует номер. Лимит ident_method501 сохраняет прежние250+пробел+250. Колонка Modification or Repair # измеряется по самому длинному option с фактическим шрифтом и отступами, вместо18%; остаток получает Description Of Modification or Repair. Проверены браузерный макет обеих тем и5тестов/139assertions.

R&M Notes layout (29/Oct/2026, уточнение): вместо textarea заметки используют однострочный input maxlength=256 и серверный notes.* max:256. Technical Notes/Add Notes/Add row расположены на уровне заголовка вне прокрутки. rm-preview-card-body — flex-column с overflow:hidden; rm-record-scroll — единая область прокрутки Notes и таблицы ремонта (flex:1,min-height:0). У Notes больше нет ограничения18vh и собственного scroll. Проверены обе темы, неподвижность заголовка на1600/1100/768/440px и лимит256/257; 5 тестов/135 assertions.

R&M Add row / Notes (29/Oct/2026): Add row рядом с Add Notes добавляет ручную строку текущего WO с ключом custom:<UUID v4> в rm_report.editor_rows. WorkorderRepairRows восстанавливает эти строки и включает в печать; они не создают TDR или общие шаблоны и не меняют ASSY. Сервер разрешает только корректные custom UUID и прежние принадлежащие WO ключи tdr:/record:. Add Notes создаёт textarea в таблице, существующие заметки редактируются там же; модального окна Notes больше нет. Сохранять несколько пробелов и переносы, фокусировать новую строку, использовать существующее автосохранение. Проверены сохранение/печать/удаление/изоляция WO (4 теста,130 assertions) и браузерный макет обеих тем, добавление/редактирование и scroll на1440/768px.

Combined Form (29/Oct/2026): в Part Processes разрешено объединять Machining AT (identity Machining) и Machining EC в одну печатную форму одной детали TDR. Использовать ProcessName::groupFormsGroupKey с collapseNdtToGroup=false для UI и серверной проверки; остальные разные Process Name, включая Machining Blend, не объединять. Каждая спецификация проверяется по собственному process_names_id исходной строки; печатный каталог включает оба выбранных имени. Это исключение только для объединения печати, не для списков выбора спецификаций. Проверены оба порядка AT/EC, запрет Blend/чужой спецификации и выбор в браузере; 4 теста/21 проверка.

Мобильная Log Card — выбор состава (29/Oct/2026): экран создания использует общую LogCardDraftChoiceGroups для IPL без конечных букв и Alternative P/N, независимо от ASSY. В мобильной версии вместо маленького Include использовать Add / Deselect (не менее 48 px); вариант выбирается нажатием всей строки (не менее 64 px), начальный выбор пустой. Выбор варианта включает группу и скрывает остальные варианты только этой группы; Deselect снова показывает весь список. Состояние скрытия пересчитывается также после восстановления черновика и распознавания P/N. исключение через Deselect сбрасывает только её вариант, повторный Add не восстанавливает его. Одиночная деталь — кнопка включения без роли radio; Add автоматически выбирает единственный вариант без предупреждения. Не выводить Part variants / Part / ASSY. Подпись детали — (IPL) P/N, исходный P/N не менять. Пустой пункт ASSY называть No ASSY: это явный выбор без сборки, сохранять assy_selection_explicit=1 и пустой assy_option_id. ASSY, Received S/N и Photo + read показывать ниже выбранного варианта, поля/фото не менее 52 px. Сохранять только включённые строки; при нажатии Add без выбранного варианта сразу показывать внутреннее предупреждение «Select a part variant.», переводить фокус на первый вариант и оставлять группу невключённой. Сохранять preview/Confirm фото и проверку горизонтального снимка. Распознанный допустимый P/N переключает вариант и видимость собственной ASSY, S/N остаётся в своей строке. Qty>1 сохраняет независимые unit_index и ASSY-select. Проверены WO108144, цепочка родителей и размеры 360/440/956 px в Chrome, фото/распознавание с тестовыми ответами, payload только выбранных строк; 34 PHP-теста/478 проверок сохранения, чтения, печати и фото. Реальный телефон в этой задаче не использовался.

Мобильная Log Card — черновик (29/Oct/2026): выбор Add/Deselect, вариант, собственные ASSY и Received S/N сохранять через user-ui-settings в БД user_ui_settings, scope mobile.log-card.draft, key wo:<id>, отдельно для текущего пользователя и WO. Browser storage не использовать. Восстанавливать только варианты/ASSY, доступные в актуальном template, без подмены исчезнувшего варианта. Автосохранение объединяет быстрые изменения и последовательно записывает последнее состояние; навигация по ссылкам приложения ждёт завершения, при сетевой ошибке сохраняет страницу и показывает внутреннее предупреждение. Для pagehide/visibilitychange использовать keepalive без системного beforeunload; внезапное закрытие ОС не даёт гарантии завершения запроса. После успешного создания Log Card очищать черновик, при ошибке создания оставлять. Подтверждённые фото отдельно сохраняются в Logs WO; в черновике хранить распознанный S/N, не бинарный файл. Проверены реальные записи/восстановление локальных настроек при переходе в Parts и обратно, последнее значение во время незавершённого запроса, Deselect, отказ записи/повтор; PHP-проверки изоляции пользователей и фото.

Log Card — снятие Include (28/Oct/2026): при снятии индивидуального Include сбрасывать radio выбора варианта только в своей строке и обновлять видимость ASSY. Log Card — подписи и выравнивание (28/Oct/2026): не выводить заголовки Part variants / Part / ASSY. Log Card — выбор вариантов (28/Oct/2026): desktop draft объединяет детали Qty=1 по IPL без конечных букв и по активным Alternative P/N, независимо от родительской ASSY. Бушинги / печатная NDT-форма (28/Oct/2026): WoBushingController::processesForm берёт спецификации по сохранённым process_id только из строк, оставшихся после фильтра партии и компонентов. Для UI/CSS задач работай медленнее и проверяй не только целевой div, но всю цепочку layout сверху вниз:
container -> page wrapper -> card -> card-body -> form -> row/grid -> column -> inner scroll area.

Перед тем как сказать, что fixed:
1. проверь родительские ограничения по width/height/min-height/overflow/display/flex/grid;
2. ищи причину на уровень выше, а не только в проблемном блоке;
3. если задача про scroll, обязательно проверь, откуда берётся ограниченная высота;
4. если задача про width/columns, обязательно проверь, что проценты считаются от нужного родителя;
5. не останавливайся на первом правдоподобном патче — доводи до реальной причины;
6. в ответе коротко указывай root cause, а не только что поменял;
7. для простых CSS/UI багов сначала делай диагностику структуры, потом patch.

При спорных визуальных багах предпочитай более глубокую проверку, даже если это медленнее.

Общее правило диагностики для этого проекта:
- Нельзя закрывать задачу на уровне "теория не сработала", "не угадал" или первого правдоподобного патча.
- Для задач поиска, данных, бизнес-логики и UI сначала проходи всю цепочку от входного действия до результата: пользовательский запрос/route -> controller/service/tool -> query/model -> реальные данные в БД/JSON -> формат ответа/рендер.
- Перед изменением кода проверь, где именно ломается фактический сценарий пользователя, а не только похожий тестовый случай.
- Если есть конкретное значение из интерфейса или базы, проверь его напрямую в текущих данных и только потом меняй код.
- После патча проверяй тем же сценарием, который не работал, плюс минимальным автотестом, если это разумно.
- В финальном ответе коротко указывай root cause и что проверено; не выдавай гипотезу за факт.
